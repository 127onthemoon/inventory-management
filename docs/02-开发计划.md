## 关键设计决策（ADR 摘要）

| 编号 | 决策 | 理由 |
|---|---|---|
| D-01 | 采用 `UPDATE product SET stock = stock - ? WHERE id = ? AND stock >= ?` 原子条件更新 | 检查与扣减在一条 SQL 内由 InnoDB 行锁串行化完成，天然防超卖，无需应用锁 |
| D-02 | 幂等号 `request_id` 唯一索引；事务内顺序为**先原子扣减、再插入单据与流水** | 相同幂等号的并发请求先在商品行锁上排队，后者插入单据时触发唯一键冲突 → 整个事务回滚（扣减被撤销）；失败回滚后幂等号随之释放，可安全重试；且所有事务都“先锁商品行”，加锁顺序一致，减少死锁 |
| D-03 | 变动后库存用 `SELECT stock ... FOR UPDATE`（当前读）获取 | 本事务已持有该行 X 锁，读到的是自己更新后的最新值，变动前 = 变动后 ∓ 数量 |
| D-04 | 死锁/锁等待超时由外层门面最多重试 3 次 | InnoDB 在唯一键冲突场景可能产生死锁，重试是官方推荐做法 |
| D-05 | 测试直接使用真实 MySQL 的独立库 `inventory_test` | H2 的锁与 MVCC 语义与 InnoDB 不同，并发测试必须在真实 MySQL 上才有说服力 |
| D-06 | 不引入 Swagger/Redis/前端框架 | 方案要求「不为技术展示而无意义增加依赖」；REST 接口在 README 中以表格+curl 示例说明 |
| D-07 | 压测登录采用表单登录 + 会话 Cookie（每线程登录一次） | 避免每个请求都做 BCrypt 校验导致结果失真 |
