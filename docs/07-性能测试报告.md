## 1. 测试环境与方法

| 项 | 值 |
|---|---|
| 硬件 | 云端开发机 8 vCPU（Intel Xeon）/ 16 GB 内存；**JMeter、应用、MySQL 部署在同一台机器**（互相争用 CPU，结果偏保守） |
| 软件 | Temurin JDK 21.0.13、Spring Boot 3.5.16（内嵌 Tomcat，最大线程 200）、HikariCP 最大 50 连接、MySQL 8.4.13、Apache JMeter 5.6.3（非 GUI 模式 `-n`） |
| 应用启动参数 | `java -Xms256m -Xmx768m -jar target/inventory-management-1.0.0.jar`（`scripts/start.sh`） |
| 压测接口 | `POST /api/stock/out`、`POST /api/stock/in`（JSON） |
| 会话 | 每个 JMeter 线程先执行一次表单登录（GET /login 提取 `_csrf` → POST /login），之后复用会话 Cookie，避免每个请求都做 BCrypt 校验 |
| 脚本 | `perf/stock-out-burst.jmx`（含同步定时器，所有线程登录后**同一时刻**发出出库请求，模拟秒杀）；`perf/stock-load.jmx`（线程持续循环，可按比例混合入库） |

| 错误统计口径 | **HTTP 200**（成功或重复提交）与 **HTTP 409**（库存不足，业务拒绝）均为系统正确处理；**其余状态码或连接失败才计为系统错误**。JMeter 断言同样只把非 200/409 标为失败 |

核对要点：
* **burst100 / burst500**：成功响应数（50）= 出库单数（50）= 库存减少量（50），最终库存 0，没有超卖；
* **idempotent**：100 个相同幂等号请求全部返回 200，但数据库中只有 1 张出库单、库存只减少 1；
* **load-depletion**：5000 件库存恰好被卖完，后续 5000 个请求全部以 409 拒绝，库存为 0 不为负；
* **mixed**：Σ入库 6914 = 期初 1000 + 2957 次 × 2 件；Σ出库 6914 = 3457 次 × 2 件；最终库存 = 1000 + 5914 − 6914 = 0，与流水净变动一致；
  入库单 2958 = 1 张期初 + 2957 次入库请求，流水 6415 = 2958 + 3457。

## 4. 性能分析

1. **热点行串行化是吞吐量上限的主要因素。** 所有请求都在争抢同一个商品行的 InnoDB 行锁，“扣减 → 当前读 → 写单据 → 写流水 → 提交”在行锁内串行执行。
   持续出库场景（load-out）单热点商品约 **633 req/s**，P95 456 ms；200 个线程排队等待同一把锁，因此平均响应时间 ≈ 并发数 / 吞吐量（200 / 633 ≈ 0.32 s），与实测 0.25 s 量级相符。
2. **库存不足的请求更快。** load-depletion 中一半请求在 `UPDATE ... WHERE stock >= ?` 处影响 0 行后立即回滚，不写单据和流水，因此整体吞吐量更高（约 960 req/s），P95 更低（360 ms）。
3. **秒杀场景响应时间较高**（burst500 P95 1078 ms）：500 个请求同一时刻到达，Tomcat 200 线程 + 连接池 50 连接构成两级排队，最后一个请求需要等前面所有请求释放行锁；但没有任何请求失败或超时。
4. **系统错误率 0%。** 全部 6 个场景（不含预热）共 30,700 个业务请求（100+500+100+10000+10000+10000），无 5xx（包括 503 并发冲突）、无连接错误。
   （注：压测时那一次应用进程的 app.log 已在之后重启时被覆盖，因此无法统计期间是否发生过被重试消化的死锁；但可以确定没有任何请求以失败告终。）
5. **测试局限**：JMeter、应用与 MySQL 在同一台 8 vCPU 机器上运行，JMeter 自身会占用大量 CPU；MySQL 使用默认配置（`innodb_flush_log_at_trx_commit=1`，每次提交刷盘）；结果仅代表课程实验环境下单热点商品的表现，不代表生产容量。

## 5. 可能的优化方向（未实施，仅作讨论）

| 方向 | 说明 | 代价 |
|---|---|---|
| 缩短行锁持有时间 | 把写流水放在扣减之前、或合并 SQL，减少锁内语句数 | 代码复杂度略增 |
| 库存分段（分桶） | 一个商品拆成 N 个库存子行，请求随机落到子行，降低单行冲突 | 查询总库存需要汇总，实现复杂 |
| 缓存预扣减（Redis Lua） | 在内存中先扣减，再异步落库 | 方案约束不允许引入 Redis；需处理缓存与数据库一致性 |
| 调整 MySQL 刷盘参数 | `innodb_flush_log_at_trx_commit=2` 可提高 TPS | 断电可能丢失最近 1 秒事务，不适合库存 |
