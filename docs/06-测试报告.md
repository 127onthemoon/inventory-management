| 场景 | 要求 | 实测 | 结论 |
|---|---|---|---|
| 库存 50，100 并发各出库 1 | 成功恰为 50、库存 0、流水一致 | 成功 50 / 拒绝 50 / 库存 0 / 出库流水 50 条（+1 条期初）/ 链连续；成功请求的“变动后库存”恰好为 0~49 各一次 | ✅ |
| 库存 50，500 并发各出库 1 | 成功 ≤ 50 且无负库存 | 成功 50 / 拒绝 450 / 库存 0 | ✅ |
| 每次 3 件，60 并发 | 不出现部分扣减 | 成功 16（48 件）/ 库存 2 | ✅ |
| 同一幂等号 100 并发 | 只扣一次 | 成功 1 + 重复 99 / 库存 49 / 出库单 1 / 所有响应单据号相同 | ✅ |
| 10 个幂等号各重复 20 次 | 恰好 10 次 | 成功 10 + 重复 190 / 库存 80 | ✅ |
| 入库+出库 300 并发混合 | 库存 = 初始 + 入 − 出，且与流水一致 | 20 + 527 − 429 = 118，实际 118；流水 301 条 = 174 + 127 张单据 | ✅ |

> 说明 1：TC-C06 中出库请求的数量与入库请求混在一起随机到达，本次运行中没有出现“库存不足”（入库在早期即补充了库存），这是真实结果；
> 库存不足与回滚场景由 TC-C01/C02/C03 及 IT-04/IT-07 覆盖。
>
> 说明 2：EXP-01 是**反例实验**：用“SELECT 读库存 → Java 计算 → UPDATE 写回”的错误写法，100 个线程都认为自己卖出成功（卖出 100 件，超卖 50 件），
> 而库存只减少了 3（丢失更新 97 次）。错误写法只存在于测试代码中，用于与正确方案对比。由于线程交错具有随机性，每次运行的具体数字会略有不同（两次运行分别为最终库存 48 和 47）。
