## 4. 方案论证：系统设计与实现

### 4.1 总体架构

单体分层架构：浏览器（Thymeleaf 页面）/ JMeter（REST）→ Spring Security → Controller（web / api）→ Service（StockService 门面 + StockTxService 事务核心）→ Repository（Spring Data JPA）→ MySQL InnoDB。（架构图与时序图见 `03-架构设计.md`）

### 4.2 数据库设计

7 张表：`sys_user`、`category`、`supplier`、`product`、`stock_in_order`、`stock_out_order`、`stock_flow`。
关键约束：`product.stock CHECK (stock >= 0)`；出入库单 `request_id`、`order_no` 唯一；流水 `ref_order_no` 唯一。（详见 `04-数据库设计.md`）

### 4.3 核心难点：高并发库存扣减

#### 4.3.1 问题

两个请求同时读到库存 1，都判断“足够”，都写回 0 —— 实际卖出 2 件，这就是**超卖 / 丢失更新**。本项目的反例实验（`NaiveDeductionExperimentTest`）真实复现了该问题：100 个线程用“读-改-写”争抢 50 件库存，**100 个线程都认为卖出成功，库存却只减少了 3**。

#### 4.3.2 方案对比

| 方案 | 能否防超卖 | 问题 | 本项目是否采用 |
|---|---|---|---|
| Java `synchronized` | 单 JVM 内可以 | 多实例失效；锁释放早于事务提交仍可能超卖；吞吐量差 | ❌（方案明确禁止仅用此法） |
| 读库存 → 内存计算 → 写回 | 不能 | 存在检查-写入时间窗口 | ❌（反例实验证明会超卖） |
| `SELECT ... FOR UPDATE` 悲观锁 + 计算 | 可以 | 多一次加锁查询，代码更长 | 部分采用（仅用于读取变动后库存） |
| 乐观锁 version 字段 | 可以 | 高冲突下大量失败重试 | ❌ |
| **原子条件更新 `stock = stock - ? WHERE stock >= ?`** | **可以** | 热点行串行化（性能上限） | ✅ 核心方案 |
| Redis 预扣减 / 消息队列削峰 | 可以 | 引入额外组件与一致性问题 | ❌（方案约束不使用） |

#### 4.3.3 实现（`StockTxService.doStockOut`，同一事务内）

```java
// ① 原子条件扣减：检查与扣减在一条 SQL 中完成，影响行数 0 = 库存不足
int updated = productRepository.decreaseStock(product.getId(), qty);
//    UPDATE product SET stock = stock - :qty WHERE id = :id AND status = 1 AND stock >= :qty
if (updated == 0) throw new InsufficientStockException(product.getName(), qty); // 回滚

// ② 当前读：本事务已持有行锁，读到的就是本次扣减后的库存
int afterStock = productRepository.currentStockForUpdate(product.getId()); // SELECT ... FOR UPDATE
int beforeStock = afterStock + qty;

// ③ 写出库单：request_id 唯一约束兜底防重复扣减
stockOutOrderRepository.saveAndFlush(order);

// ④ 写库存流水（ref_order_no 唯一）
stockFlowRepository.saveAndFlush(flow);
```

原理：InnoDB 执行 UPDATE 时对该行加排他锁并读取**最新已提交版本**（当前读），多个事务对同一商品的扣减被数据库串行化；后到者看到前者提交后的库存，条件不满足即影响 0 行。行锁持有到提交，保证“库存 + 单据 + 流水”原子可见。

#### 4.3.4 防重复提交（幂等）

三层保护：① 页面表单打开时生成 UUID 作为 `requestId` 隐藏域，提交按钮点击后禁用；② 门面服务先按 requestId 查询，已存在则直接返回首次结果（`duplicate=true`）；③ 数据库唯一约束：两个相同 requestId 的请求同时通过第②步时，会在商品行锁上排队，后者插入单据触发唯一键冲突 → **整个事务回滚、扣减被撤销** → 门面捕获异常后返回首次结果。

#### 4.3.5 异常回滚与重试

* 任何运行时异常（库存不足、约束冲突、数据库错误）都导致事务整体回滚；测试 IT-07 验证“扣减已执行、写单据失败”时库存恢复。
* 死锁 / 锁等待超时（`PessimisticLockingFailureException`）在事务外退避重试最多 3 次；之所以拆成两个 Bean，是因为 Spring `@Transactional` 基于代理，且重试必须在事务之外开启新事务。

### 4.4 权限与安全实现

Spring Security 表单登录 + BCrypt；`/users/**` URL 级限制 ADMIN；基础资料增删改方法上 `@PreAuthorize("hasRole('ADMIN')")`；页面 CSRF 开启、`/api/**` 关闭；接口未登录 401 / 无权限 403 JSON。

### 4.5 界面实现

Thymeleaf 片段布局（`fragments/layout.html`：左侧导航 + 顶栏 + 消息提示 + 内容区），单个 `app.css`（CSS 变量统一配色、卡片、表格、徽标、表单、分页、柱状图）与 `app.js`（防重复提交、删除确认、分页保留查询参数、选择商品显示当前库存）。界面截图见 `docs/screenshots/`。

## 6. 总结与反思

本人体会：这次课设之前，我对“超卖”的理解其实很浅，总觉得先查一下库存够不够，够了再减就行。自己对照看了反例实验，才知道问题出在哪儿：100 个线程都先读后写，结果个个都显示成功，库存却只少了 3。也就是说，读和写中间那段空隙里，别人已经改过了，自己还按旧值往回写，账面和实际对不上。后来改成数据库里那条原子条件更新，判断和扣减写在同一条 UPDATE 里，100 个或者 500 个请求一起去抢 50 件库存，成功的正好是 50，最后库存是 0，流水也对得上。这两套结果摆在一起，比只听一句“不能用先读后写”要清楚得多。

事务和回滚也是做完才有感觉。出库不只是改一个数字，还要写单据、写流水，这几步必须一块儿成功，或者一块儿撤掉。测试里有过扣减已经做了、后面写单据失败的情况，库存能回到原来的 10，并且没有留下单据和流水，我才觉得这套设计靠得住。幂等号也是一样。同一个 request_id 提交很多次，包括 100 个请求一起过来，都只扣一次、只留一张单。这比单纯在页面上把按钮禁用要扎实，因为刷新或者重复点提交，照样防得住。

压测这部分，我是后来才学会看 P95 的。平均值容易被很快返回的请求拉低，P95 更能看出大部分请求等到了什么程度。报告里持续出库是 632.83 次/秒，P95 是 456 毫秒；快要卖光的场景吞吐量更高，有 959.51 次/秒，P95 反而只有 360 毫秒，因为它有一半请求在库存不足时立刻退回，不用再写单据。混合出入库合计大约 899.36 次/秒。这些数字都是 JMeter、应用和 MySQL 放在同一台机器上跑出来的，只能说明这门课实验环境下的情况，不能当成生产指标。

还有一点我觉得比较深：AI 帮忙写的代码，不能看它能编译就直接当作业交。项目里启动时校验失败、测试断言写错，都是跑起来对着报错改才过的。我后来会自己翻核心 SQL 和事务代码，再对一下 mvn test 的 49 个用例，以及页面巡检、冒烟测试的结果。现在回头看，系统还只是单机部署，也没有做缓存，要是场景再大一点，这些都还得另外想办法。
