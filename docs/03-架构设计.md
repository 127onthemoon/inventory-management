# 系统架构设计

## 1. 总体架构

采用**单体分层架构**（Spring Boot 3.5 单个可执行 jar），浏览器通过 Thymeleaf 服务端渲染页面，脚本/压测工具通过 REST 接口访问，所有数据存储在 MySQL 8.4（InnoDB）。

```
┌──────────────┐   ┌──────────────┐
│   浏览器      │   │ JMeter/curl   │
│ (HTML/CSS/JS) │   │  (JSON API)   │
└──────┬───────┘   └──────┬───────┘
       │ 表单登录 + CSRF     │ 会话 Cookie / HTTP Basic
┌──────▼──────────────────▼─────────────────────────────┐
│ Spring Security 过滤器链：认证、URL 角色控制、CSRF、401/403 │
├──────────────────────────────────────────────────────┤
│ Controller 层                                          │
│  controller.web  (Thymeleaf 页面，@PreAuthorize 方法级权限) │
│  controller.api  (REST，统一 ApiResponse + 异常→状态码映射)  │
├──────────────────────────────────────────────────────┤
│ Service 层                                             │
│  StockService（门面：幂等快速路径、死锁重试，不开事务）       │
│     └─► StockTxService（@Transactional：原子扣减→当前读→单据→流水）│
│  ProductService / CategoryService / SupplierService     │
│  UserService / StatisticsService（统计 + 一致性核对）       │
├──────────────────────────────────────────────────────┤
│ Repository 层（Spring Data JPA；库存变更使用原生条件 UPDATE）   │
├──────────────────────────────────────────────────────┤
│ MySQL 8.4 InnoDB：行级锁、事务、唯一约束、CHECK 约束、外键      │
└──────────────────────────────────────────────────────┘
```

## 4. 模块关系

```
            ┌────────────┐
            │  Category   │◄──────────┐
            └────────────┘           │ N:1
            ┌────────────┐     ┌─────┴──────┐
            │  Supplier   │◄────│  Product    │ stock 只读映射
            └─────▲──────┘ N:1 └─────▲──────┘
                  │                  │ N:1
        ┌─────────┴───┐  ┌───────────┼────────────┐
        │ StockInOrder │  │StockOutOrder│ StockFlow │  ← 同一事务写入
        └──────────────┘  └────────────┴───────────┘
User（独立，用于登录与权限；单据中记录操作人用户名）
```

* **基础资料模块**（分类/供应商/商品）只维护资料，**不改变库存**；`Product.stock` 在 JPA 中映射为 `insertable=false, updatable=false`，框架层面杜绝“实体写回库存”。
* **库存作业模块**（入库/出库）是唯一能改变库存的入口，统一经过 `StockService → StockTxService`。
* **统计模块**只读；一致性核对同时提供页面（/consistency）、接口（/api/stock/consistency）与 SQL 脚本三种方式。

## 5. 出库请求处理时序（核心）

```
Controller            StockService(门面)               StockTxService(@Transactional)          MySQL
   │ stockOut(req)          │                                   │                                │
   │──────────────────────►│ 校验数量>0                          │                                │
   │                        │ findByRequestId(rid) ─────────────────────────────────────────────►│ 快速幂等检查
   │                        │  已存在 → 返回 duplicate=true        │                                │
   │                        │ doStockOut() ────────────────────►│ BEGIN                          │
   │                        │                                   │ ① UPDATE product SET stock=stock-? │
   │                        │                                   │    WHERE id=? AND status=1 AND stock>=?  (加行 X 锁)
   │                        │                                   │    影响 0 行 → 抛库存不足 → ROLLBACK │
   │                        │                                   │ ② SELECT stock … FOR UPDATE（当前读）│
   │                        │                                   │ ③ INSERT stock_out_order (request_id 唯一)
   │                        │                                   │ ④ INSERT stock_flow (ref_order_no 唯一)
   │                        │                                   │ COMMIT（释放行锁）               │
   │                        │◄──────── 结果 / 异常 ──────────────│                                │
   │                        │ 唯一键冲突 → 查已存在单据 → duplicate │                                │
   │                        │ 死锁/锁超时 → 退避后新事务重试(≤3次)    │                                │
   │◄───────────────────────│                                   │                                │
```

## 6. 并发控制设计要点

| 风险 | 方案 | 代码位置 |
|---|---|---|
| 超卖 / 负库存 | 原子条件更新 `stock = stock - ? WHERE stock >= ?`；DB `CHECK (stock >= 0)` 兜底 | `ProductRepository.decreaseStock`、schema.sql |
| 丢失更新（入库与出库互相覆盖） | 入库也用 `stock = stock + ?`，读-改-写由数据库在行锁内完成 | `ProductRepository.increaseStock` |
| 变动前后库存记录不准 | 本事务持有行锁后用 `SELECT … FOR UPDATE` 当前读 | `ProductRepository.currentStockForUpdate` |
| 重复提交 / 重复扣减 | 前端按钮禁用 + 幂等号快速路径 + `request_id` 唯一约束 + 冲突后整体回滚 | `StockService`、schema.sql |
| 单据、流水、库存不一致 | 四步在同一事务；任一步异常整体回滚；`ref_order_no` 唯一保证一单一流水 | `StockTxService` |
| 死锁 / 锁等待超时 | 捕获 `PessimisticLockingFailureException`，退避后开启新事务重试 ≤ 3 次 | `StockService` |
| 单据号碰撞 | AtomicInteger 序号 + 唯一约束 + 冲突换号重试 | `OrderNoGenerator`、`StockService` |

**为什么拆成两个 Bean？** Spring 的 `@Transactional` 基于 AOP 代理，类内自调用不会生效；同时“重试”必须发生在事务之外，每次重试开启全新事务，因此门面（StockService，无事务）调用事务核心（StockTxService）。

## 7. 安全设计

* 认证：表单登录（`/login`），BCrypt 密码；REST 接口额外支持 HTTP Basic（便于 curl 演示）。
* 授权：URL 级 `/users/** → ADMIN`；方法级 `@PreAuthorize("hasRole('ADMIN')")` 控制基础资料增删改。
* CSRF：页面表单开启（Thymeleaf 自动注入 `_csrf`）；`/api/**` 关闭 CSRF（接口无浏览器自动提交风险，且需登录）。
* 未登录访问接口返回 401 JSON、无权限返回 403 JSON；页面则跳转登录页 / 显示 403 页。
* 所有 SQL 使用 JPA/命名参数，杜绝 SQL 注入。

## 8. 异常与状态码约定（REST）

| 场景 | HTTP | code |
|---|---|---|
| 成功 | 200 | OK |
| 重复提交（未重复执行） | 200 | DUPLICATE |
| 参数校验失败 | 400 | VALIDATION_ERROR |
| 业务规则违反（停用商品、数据完整性等） | 400 | PRODUCT_DISABLED / DATA_INTEGRITY … |
| 未登录 / 无权限 | 401 / 403 | UNAUTHORIZED / FORBIDDEN |
| 商品不存在 | 404 | NOT_FOUND |
| **库存不足（业务拒绝）** | **409** | INSUFFICIENT_STOCK |
| 并发冲突重试后仍失败 | 503 | CONCURRENT_CONFLICT |
| 未预期的系统错误 | 500 | SYSTEM_ERROR |

压测统计时，200 与 409 都属于“系统正确处理”，只有 5xx / 连接失败计为系统错误。
